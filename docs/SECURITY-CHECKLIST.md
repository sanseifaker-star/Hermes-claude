# Security checklist — Hermes Agent self-hosted

Основано на публичном аудите безопасности hermes-agent
([issue #7826](https://github.com/NousResearch/hermes-agent/issues/7826),
v0.8.0, 4 critical / 9 high) и официальной документации. Версия, которую вы
поставите, может отличаться — сверяйтесь с CHANGELOG.

Контекст этой установки: агент работает **от root** и принимает команды из
Telegram. Это значит: кто получит доступ к боту — получит сервер. Всё ниже
исходит из этого.

## До установки

- [ ] Знаете свой numeric Telegram ID (`@userinfobot`) — он понадобится
      для allowlist.
- [ ] Токен бота от `@BotFather` под рукой, но вводится **только на
      сервере**. Не в чат, не в git, не в issues.
- [ ] Провайдер модели проверен на tool-calling:
      `./scripts/check-tools-support.sh <base_url> <model> <api_key>`.
      Модель с контекстом от 64K токенов — иначе многошаговая работа
      разваливается.

## Обязательный минимум после установки

Три вещи, без которых бота с root-доступом запускать нельзя.

- [ ] **Allowlist в `~/.hermes/.env`:**
      ```
      TELEGRAM_ALLOWED_USERS=ВАШ_ID
      ```
      Несколько пользователей — через запятую. Проверьте, что
      `GATEWAY_ALLOW_ALL_USERS` **не** выставлен в `true`.

- [ ] **Approvals в ручном режиме:**
      ```bash
      hermes config set approvals.mode manual
      ```
      `manual` — спрашивать перед опасными командами (по умолчанию).
      `smart` — решение отдаётся вспомогательной LLM; аудит (H2) прямо
      против этого. `off` — YOLO, снимает все проверки.

- [ ] **Никогда не запускать с `--yolo`** на этой машине. Флаг снимает
      проверки на один запуск (H1). Допустим только в изолированной
      песочнице, которой у нас нет.

## Дополнительно, по ситуации

- [ ] **Terminal backend.** По умолчанию `local` — команды выполняются
      прямо на хосте с правами root (C1). Для недоверенного кода:
      ```bash
      hermes config set terminal.backend docker
      ```
      Оговорка из аудита (C3): approval-проверки в контейнерных бэкендах
      могут пропускаться безусловно. Контейнер снижает ущерб хосту, но не
      заменяет ревью действий.

- [ ] **Рабочая директория.** Ограничить, где агент работает по умолчанию:
      ```bash
      hermes config set terminal.cwd /absolute/path
      ```
      Это не песочница — доступ к остальной ФС остаётся (C2), но снижает
      шанс случайной правки не там.

- [ ] **Skills.** Агент создаёт их сам, они сохраняются в
      `~/.hermes/skills/` и подгружаются в будущих сессиях — то есть
      живут дольше разговора (C4). Раз в пару недель:
      `ls ~/.hermes/skills/` и посмотреть, что накопилось.

- [ ] **Prompt injection через context files.** `AGENTS.md`, `.hermes.md`,
      `CLAUDE.md`, `.cursorrules` из чужих репозиториев попадают в system
      prompt. Не открывать untrusted repo с включёнными tools на `local`
      бэкенде.

- [ ] **Зафиксировать версию.** `hermes update` не запускать вслепую —
      сначала читать changelog (H9).

- [ ] **Файрвол.** Внутрь только SSH. Telegram работает исходящим
      long-polling, входящие порты боту не нужны.

- [ ] **Секреты.** `~/.hermes/.env` с правами `600`, не в git. При утечке
      токена — отозвать у BotFather, ключи — у провайдера.

## Проверка, что защита реально работает

Не верьте отчётам агента о собственных действиях — проверяйте результат.
Это не паранойя: провайдер без tool-calling заставляет агента рапортовать
об успехе там, где он физически ничего не сделал.

```
# в Telegram
запиши строку TEST-1 в /root/.hermes/probe.txt

# на сервере
cat /root/.hermes/probe.txt
stat /root/.hermes/probe.txt
```

Та же логика для approvals: попросите что-нибудь заведомо опасное и
убедитесь, что он **спросил**, а не сделал.
